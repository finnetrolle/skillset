# Двухосевое ревью изменений

Ревью диффа вдоль двух независимых осей:

- **Standards** - код следует документированным стандартам этого репозитория и не
  несёт код-запахи из базовой линии ниже.
- **Spec** - изменения верно и полностью реализуют задачу, по которой делались,
  и только её.

Обе оси выполняются **параллельными саб-агентами**, чтобы контексты осей не
загрязняли друг друга; этот скилл агрегирует их находки.

Правило режима: скилл read-only относительно кода, требований и существующих
пользовательских файлов. Сохраняй собственные результаты по
[контракту evidence](../verify-changes/references/acceptance-evidence.md); прочитай
его перед первым ревью. Судьба находок - решение пользователя.

## Почему две оси

Изменение может проходить по одной оси и проваливать другую:

- код безупречен по стандартам, но делает не то, что просила задача -
  Standards pass, Spec fail;
- код делает ровно то, что в задаче, но ломает конвенции проекта -
  Spec pass, Standards fail.

Отчёты по осям никогда не сливаются и не переранжируются: одна ось не должна
маскировать другую. Итогового "победителя" между осями не выбирается.

## Шаг 1. Зафиксировать точку сравнения

- Если пользователь назвал точку (SHA, ветка, тег, `main`, `HEAD~5`) - сначала
  разрешить её и вычислить `merge-base` с `HEAD`. Ревьюить
  `git diff <merge-base>`: такой diff включает committed изменения после базы,
  staged и unstaged изменения. Отдельно получить список коммитов
  `git log <точка>..HEAD --oneline` и содержимое всех untracked-файлов.
- Если точка не названа и рабочее дерево грязное - точка `HEAD`, дифф
  `git diff HEAD` плюс всё содержимое untracked-файлов (`git status`): их
  содержимое тоже часть сделанной работы.
- Если точка не названа и дерево чистое - спросить. Не угадывать.

До запуска саб-агентов проверить, что точка разрешается (`git rev-parse`),
`merge-base` существует и полный diff вместе с untracked-файлами непуст. Битый
ref или пустой scope должен останавливаться здесь, а не внутри двух параллельных
саб-агентов.

## Шаг 2. Определить источник задачи (для Spec-оси)

В порядке приоритета:

1. Задача, названная пользователем (issue, spec, ticket) - читать целиком:
   результат, требования, критерии готовности, раздел "Не входит".
2. Ссылки на задачи в сообщениях коммитов (`#123`, `Closes #45`).
3. Spec/issue-файлы среди изменённых: статусы и чекбоксы в diff обычно указывают
   на выполненную задачу. Прочитать её.
4. Ничего не нашлось - спросить пользователя, против чего сверять. Если задачи
   нет - Spec-саб-агент пропускается, в финальном отчёте помечается
   "задача не предоставлена".

Сверять против полного согласованного источника задачи с явными последующими
уточнениями пользователя; не подменять его пересказом агента.

## Шаг 3. Определить источники стандартов (для Standards-оси)

Всё, что в репозитории документирует, как писать код: `CLAUDE.md`/`AGENTS.md`,
`CODING_STANDARDS.md`, `CONTRIBUTING.md`, README-секции про конвенции,
 conventions для work-item/spec-файлов, если diff их правит.

Пропускать то, что уже принуждает тулинг (lint, static analysis, formatter,
wired-в-build проверки) - дублировать их находки не нужно.

Поверх стандартов репозитория Standards-ось всегда несёт **базу запахов**
ниже. Два правила:

- **Стандарт репозитория главнее.** Где документированный стандарт одобряет то,
  что база бы пометила, - запах подавляется.
- **Всегда judgement call.** Каждый запах - помеченная эвристика ("возможный
  Feature Envy"), не жёсткое нарушение.

## Шаг 4. Запустить оба саб-агента параллельно

Обоим передать: команду диффа, список коммитов (если есть), список untracked
файлов. Обоим запретить изменять исходный код, требования и пользовательские
файлы. Отчёты пишутся по-русски; цитаты спеки и имена запахов - в оригинале.
Лимит 400 слов относится к резюме; полный отчёт сохраняет все findings и
criterion-to-evidence строки.

### Standards-саб-агент

Передать: источники стандартов из шага 3 **плюс базу запахов из шага 3 целиком**
(у саб-агента другого доступа к ней нет). Задание:

"Выполни эту ось самостоятельно: не вызывай `two-axis-review` повторно
и не создавай дополнительных агентов. Проверь дифф по стандартам репозитория.
Отчитайся по файлам/хункам:
(a) каждое место, где дифф нарушает документированный стандарт - со ссылкой на
стандарт (файл + правило); (b) каждый замеченный запах базы - назови его и
процитируй ханк. Различай жёсткие нарушения и judgement call: breach
документированного стандарта может быть жёстким, запах базы - всегда judgement
call, документированный стандарт репозитория перекрывает базу. Пропускай то, что
принуждает тулинг. Резюме до 400 слов, полный отчёт без потери находок."

### Spec-саб-агент

Передать: путь или содержимое задачи из шага 2. Задание:

"Выполни эту ось самостоятельно: не вызывай `two-axis-review` повторно
и не создавай дополнительных агентов. Проверь дифф против задачи. Отчитайся:
(a) таблица соответствия: строка на каждый критерий готовности / требование;
колонки - требование (цитата), где реализовано (файл:строка или тест), вердикт
(выполнено / частично / не выполнено / не проверяемо статически). Критерий
'тест существует' проверять по факту наличия теста, не по чекбоксу в issue;
частично выполненный критерий не засчитывать как выполненный; 'build проходит' -
либо пометить как перепроверено, либо 'принимается по заявлению'.
Отдельно ищи требования, которые выглядят выполненными, но реализованы неверно.
Для каждого укажи ошибочное поведение, место в коде и нарушенный пункт задачи;
такой критерий не отмечай выполненным.
(b) нарушения границ: каждый пункт 'Не входит' / out of scope найти в диффе;
нарушение границы серьёзнее лишнего хелпера - это незаказанная поверхность
поддержки.
(c) gold-plating: сущности, не вытекающие ни из одного критерия (функции,
опции конфигурации, абстракции 'на будущее', тесты несуществующего поведения,
док-секции о незаказанном). Каждую находку классифицировать: лишнее / оправдано
(одной фразой почему) / пограничное.
(d) посторонние задачи в дереве: изменённые и untracked-файлы вне scope задачи;
рекомендовать отдельный коммит. Резюме до 400 слов, полная таблица без пропуска критериев."

## Повторное ревью после исправлений

Первый проход всегда покрывает полный согласованный scope двумя независимыми
осями. Сохранить base, источник задачи, manifest проверенных файлов и findings.
Явные уточнения пользователя изменяют контракт; зафиксировать их вместе с source.

После согласованной волны фиксов продолжить тех же двух рецензентов: передать
delta с предыдущего проверенного состояния, прежние findings, изменённые
контракты, затронутых consumers и актуальную evidence. Каждый проверяет закрытие
своих находок и новые риски delta. Неизменённые файлы сохраняют предыдущий verdict;
это явно указать, а не изображать повторное чтение всего проекта.

Изменение общего helper/контракта расширяет scope до его consumers. При потере
контекста, неподтверждённом manifest/source или широком изменении границ сделать
новый полный проход. Review результата фиксируется только для проверенного
состояния; позднейшие правки требуют анализа влияния. Оси остаются независимыми.

## Шаг 5. Агрегировать

Сохрани полные результаты обеих осей отдельными файлами в evidence-пакете,
привязанном к source, base и проверенному состоянию. Для delta-review добавляй
новый пакет со ссылкой на предыдущий; прежние вердикты сохраняй. В финальном
ответе укажи manifest и пути обоих отчётов.

Представить оба отчёта под заголовками `## Standards` и `## Spec` - дословно
или с лёгкой чисткой. Не сливать и не переранжировать находки.

Завершить однострочным итогом: количество находок по каждой оси и худшая
проблема **внутри каждой оси** (если есть). Не выбирать единого победителя
между осями - это переранжирование, которое разделение осей существует, чтобы
предотвратить.

Не предлагать исправлений кода самому. Если пользователь просит починить
находку - это уже отдельная задача, не часть этого скилла.

## База запахов (Fowler, Refactoring, гл. 3)

Каждый запах читается как "что это" -> "как чинить". Сравнивать с диффом:

- **Mysterious Name**: имя функции, переменной или типа не раскрывает, что она
  делает или хранит. -> переименовать; если честного имени не находится -
  дизайн мутный.
- **Duplicated Code**: одна и та же форма логики встречается больше чем в одном
  хунке или файле изменения. -> извлечь общую форму, звать из обоих мест.
- **Feature Envy**: метод лезет в данные другого объекта больше, чем в свои.
  -> перенести метод на данные, которым он завидует.
- **Data Clumps**: одни и те же несколько полей или параметров постоянно ходят
  вместе (тип, который хочет родиться). -> собрать в один тип, передавать его.
- **Primitive Obsession**: примитив или строка вместо доменной концепции,
  заслуживающей своего типа. -> дать концепции свой маленький тип.
- **Repeated Switches**: один и тот же `switch`/каскад `if` по одному типу
  повторяется по изменению. -> полиморфизм или одна карта, общая для обоих мест.
- **Shotgun Surgery**: одно логическое изменение заставляет правки по многим
  файлам диффа. -> собрать меняющееся вместе в один модуль.
- **Divergent Change**: один файл или модуль правится по нескольким несвязанным
  причинам. -> разделить так, чтобы каждый модуль менялся по одной причине.
- **Speculative Generality**: абстракции, параметры или хуки под потребности,
  которых у задачи нет. -> удалить; инлайнить обратно до реальной нужды.
- **Message Chains**: длинная навигация `a.b().c().d()`, от которой вызывающий
  не должен зависеть. -> спрятать обход за одним методом первого объекта.
- **Middle Man**: класс или функция, которая в основном только делегирует
  дальше. -> убрать, звать реальную цель напрямую.
- **Refused Bequest**: наследник или реализатор, игнорирующий большую часть
  унаследованного. -> выбросить наследование, использовать композицию.
