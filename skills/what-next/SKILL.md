# what-next: выбор следующей issue

Задача: по реестру work items предложить от 1 до 3 вариантов следующей issue
с обоснованием. Skill read-only: ничего не правит, не начинает реализацию,
заканчивается вопросом о выборе.

## Входные данные

1. Реестр: `spec/WORK_ITEMS.md` - таблица work items со статусами и прогрессом.
2. Epic-файлы: `spec/epics/epic_NN_*.md` - checklist дочерних issues,
   зависимости, «предпочтительный порядок» (мягкие ограничения, не блокировки).
3. Сами issue-файлы кандидатов: `spec/issues/**`. Статус в заголовке дочерней
   issue - источник истины, реестр и checklist - сводное представление.
4. `git log --oneline -15` - недавняя активность и возможная рассинхронизация
   статусов. Git log не меняет статус issue и не доказывает `Done`.

Если реестра нет - просканировать `spec/issues/` напрямую по статусам в
заголовках. Если и этого нет - сказать об этом и остановиться.

## Порядок работы

1. Прочитать реестр и epic-файлы.
2. Одним поиском извлечь из issue-файлов заголовок, статус, epic, зависимости,
   оценку и уверенность. На этом проходе не читать целиком все issues.
3. Построить фронтир по формальным статусам и зависимостям.
4. Проверить свежий `git log`. Если commit или код похожи на реализацию issue,
   которая ещё не `Done`, прочитать её критерии и релевантный diff/код. Это
   рассинхронизация для отчёта, а не разрешение молча считать issue закрытой.
   Если задача уже проходила приёмку, прочитай её сохранённый manifest и
   [контракт evidence](../verify-changes/references/acceptance-evidence.md).
   Раздели исторический результат, текущую применимость и незавершённое closure.
   Перезаписанный build-отчёт не отменяет историческое прохождение; старый PASS
   не подтверждает текущее дерево. Не запускай проверки ради восстановления
   истории и не предлагай повторную реализацию уже доказанных критериев.
   Если пакет недоступен, явно укажи пробел в evidence, не подменяя его выводом
   о том, что реализация отсутствует.
5. По metadata и tie-breakers выбрать до пяти близких кандидатов, прочитать их
   целиком, проверить фактические швы в коде и сократить ответ до 1-3 вариантов.

## Отбор кандидатов

Кандидат проходит фильтр, когда:

- статус самой issue - `Ready for implementation` или `In progress`;
- все issues из «Зависит от» имеют статус `Done`;
- epic-родитель, если он есть, имеет статус `Ready for implementation` или
  `In progress`; самостоятельная issue допустима без epic-родителя.

Статус в issue-файле - источник истины. Реестр, checklist, commits и наличие
кода только помогают обнаружить рассинхронизацию. Не повышать статус до `Done`
по имени коммита или наличию реализации. Если работа уже видна, но issue не
`Done`, не предлагать реализовать её заново: предлагать проверить оставшиеся
критерии и довести текущую issue до закрываемого состояния.

Tie-breakers (в порядке убывания веса):

1. Продолжение самой issue в статусе `In progress` или доведение обнаруженной
   незакрытой работы ценнее старта ещё одной issue.
2. Явное нарушение мягкого порядка из epic исключать не должно, но кандидаты,
   соблюдающие порядок, ранжируются выше.
3. Переиспользование: issue, строящая инфраструктуру (fixture, SDK, контракт)
   для последующих issues, ценнее issue того же размера без такого эффекта.
4. Закрытие непроверенного допущения (uncertainty reduction) ценнее рутины.
5. Прогресс к `Done` текущего `In progress` эпика ценнее старта нового.
6. Меньший размер / меньше риска - при прочих равных.

Не предлагать issue по памяти или только по заголовку. Финальные 1-3 варианта
обязательно прочитать целиком.

## Формат ответа

Ответ - caveman full на языке пользователя: короткие фразы, фрагменты, без
воды и вступлений. Технические термины, ID, статусы, названия конфигов - точно
как в исходниках. Эм-dash не использовать (правило пользователя). Таблицы и
emoji не нужны.

Структура - ровно такая:

```
Фронтир: <список незаблокированных ID>. Мягкий порядок эпика: <одной строкой>.
Рассинхронизация: <нет или ID: status в spec; наблюдаемый сигнал; что ещё надо проверить>.

## Вариант 1: <ID> - <название>
Статус: <...>. Оценка: <...>. Уверенность: <...>.
Делать: <3-7 пунктов или плотный абзац: суть реализации, тестовый seam, подход>
Value: <честно: product-фича или verification-increment; что станет фактом,
которым раньше было утверждением; что переиспользуется дальше>
Проверка руками: <что пользователь проверяет сам после Done: запуск бинарника,
docker-образ, конфиг, логи - то, что не покрывает ./gradlew build>

## Вариант 2: ... (если есть)
## Вариант 3: ... (если есть)

Рекомендация: <ID>.
Почему: <1-3 причины, привязанные к tie-breakers>.
Траектория: <цепочка ID через дефис, как эпик закрывается>.

Начинать <ID>?
```

Правила по блокам:

- «Делать» - план на уровне файлов/швов, не пересказ acceptance criteria.
  Проверить фактическое состояние кода (grep/чтение), spec-утверждения о
  текущем коде подтверждать глазами.
- «Value» - без приукрашивания. Если функциональность не растёт - так и
  писать: verification increment, назвать, что именно становится защищённым.
- «Проверка руками» - извлечь из критериев готовности issue пункты, которые
  не покрываются автоматизацией (реальный запуск, внешние системы, глазами).
  Если таких нет - явно написать «не осталось, всё покрыто build».
- Вариантов 1-3. Один - когда фронтир реально узкий или ответ очевиден;
  три - когда есть живая развилка. Промежуточные дубликаты не тащить.
- Рекомендация ровно одна. Если у пользователя запрошен только совет без
  выбора - всё равно дать рекомендацию, решение остаётся за ним.

## Ограничения

- Ничего не менять в spec/, коде, реестре.
- Не начинать реализацию выбранной issue без отдельного указания.
- Не выдумывать issues, которых нет в реестре.
- Если все кандидаты заблокированы или реестр пуст - доложить состояние
  фронтира и остановиться без вариантов.
