# Сервер и доступ

Читать при проверке выбранного сервера, запуске локального Docker и настройке
доступа. Параметры сначала определить по шагу 0 основного скилла.

## Настроенный сервер

Использовать выбранный `SONAR_HOST_URL`, включая нестандартный порт и path
prefix. Проверить `api/system/status` ограниченным HTTP-запросом; состояние
готовности - `UP`. Общий timeout ожидания по умолчанию 180 секунд. Записать
версию из ответа или `api/server/version`. Ошибку TLS/HTTP/авторизации
диагностировать, не отключая проверку сертификатов.

Для удалённого или уже доступного сервера Docker не нужен. Для локального
неработающего сервера сначала определить его существующий контейнер/service
по конфигурации, image и port mapping. Проверить `docker info` с внешним
timeout 10 секунд. Если CLI завис, завершить его и сообщить infrastructure
failure. Запустить остановленный подходящий контейнер или Compose service;
не пересоздавать его ради неизвестного пароля или обновления версии.

## Новый локальный сервер

Только когда сервер ещё не настроен и выбран локальный режим:

- выбрать свободный loopback-порт, по умолчанию 9000. Если он занят другим
  сервисом, выбрать другой порт и сообщить URL; не переключать сервер при
  сбое явно заданного URL;
- получить Docker-safe `SONAR_CONTAINER_NAME` из уникального project slug;
  проверить, что одноимённый контейнер не относится к другому проекту;
- выбрать совместимый Community image с явным version tag или digest.
  Если его нет в конфигурации, проверить текущую официальную документацию,
  доступный tag и runtime/architecture requirements; не обновлять существующий
  сервер и не подменять выбранную версию плавающим `latest`;
- создать или переиспользовать подходящие named volumes для data, extensions
  и logs. Сохранять существующие mounts; не удалять контейнеры/volumes с данными.

Пример после определения параметров; именованные volumes Docker создаёт
при первом использовании:

```bash
docker run -d --name "$SONAR_CONTAINER_NAME" \
  -p "127.0.0.1:${SONAR_PORT}:9000" \
  -v "${SONAR_CONTAINER_NAME}-data:/opt/sonarqube/data" \
  -v "${SONAR_CONTAINER_NAME}-extensions:/opt/sonarqube/extensions" \
  -v "${SONAR_CONTAINER_NAME}-logs:/opt/sonarqube/logs" \
  "$SONAR_IMAGE"
```

Дождаться `UP`, затем завершить первичную настройку доступа поддержанным этой
версией способом, включая обязательную смену начального пароля. Встроенная
локальная база - для анализа на машине, не шаблон production-развёртывания.

## Доступ без привязки к агенту

1. Использовать действующий `SONAR_TOKEN` из окружения или проектного secret
   store. Уже используемый защищённый env-файл также подходит, включая
   `.claude/sonar.env`; это совместимый источник, а не обязательное расположение.
2. Env-файл читать как данные только по ожидаемым ключам (`SONAR_TOKEN`, при
   необходимости `SONAR_ADMIN_USER`/`SONAR_ADMIN_PASSWORD`). Не исполнять его
   через `source`/`eval`, не печатать содержимое или значения секретов.
3. Если нужно сохранить новый токен и проект не задаёт secret store, использовать
   пользовательский конфиг вне репозитория:
   `${XDG_CONFIG_HOME:-$HOME/.config}/analyze-via-sonar/<project-slug>/sonar.env`.
   Каталог ограничить правами 700, файл - 600. При хранении внутри проекта
   сначала убедиться, что файл исключён из Git и не отслеживается.
4. Проверить существующий токен через `api/authentication/validate`, затем
   необходимые права на анализ и чтение результатов. Для Web API предпочитать
   `Authorization: Bearer <token>`; для совместимых версий с Basic token auth
   curl использовать `-u "$SONAR_TOKEN:"`, чтобы он не спрашивал пароль.
   Следовать документации выбранного сервера/API.
5. Рабочий токен переиспользовать. При 401 или отсутствии токена запросить
   настройку доступа через защищённый источник; при 403 определить недостающие
   права. Не менять пароль и не пересоздавать сервер как способ обхода ошибки.
6. Генерировать токен через `api/user_tokens/generate` только при наличии
   согласованного доступа для управления токенами. Тип и scope выбрать по
   требуемым операциям: analysis-only token может не разрешать чтение findings.
   Имя получить из текущего project slug и назначения; не отзывать чужие или
   рабочие токены из-за совпадения фиксированного имени.

Пароль администратора не нужен для каждого запуска. Для scanners с поддержкой
`SONAR_TOKEN` использовать окружение. Если scanner требует другой механизм,
выбрать поддержанный защищённый config/secret input; при необходимой передаче
через CLI скрывать значение в tool output и отключать echo/tracing. Секреты
не помещать в отслеживаемые `sonar-project.properties`, build-файлы или отчёты.
