# Верификация с актуальной evidence и ревью delta

Скрипты выполняют механические проверки; LLM оценивает смысл и разрешённые
исправления. Финальный PASS требует всех применимых гейтов для одного конечного
состояния. Экономия получается от ранней обратной связи и повторного использования
действительных результатов, а не от сокращения обязательного покрытия.

## Авторизация и scope

По умолчанию проверка read-only. Явное «исправляй до полного прохода» или
«закрой issue по пайплайну» заранее разрешает исправления внутри scope. Второй
запрос также разрешает завершить issue по протоколу репозитория после
прохождения применимых гейтов и повторной проверки итогового состояния;
обычный запрос на проверку и один лишь $verify-changes не разрешают менять
completion status. Без авторизации на исправления собрать конкретные findings
и запросить решение один раз для волны. Не коммитить, не
пушить и не создавать PR. Не менять пользовательские требования или спорный
scope ради PASS. Не повторять уже согласованный вопрос.

- Named base: проверить ref и использовать merge-base с HEAD плюс staged,
  unstaged и untracked. Dirty tree без base: HEAD. Чистое дерево без base:
  спросить; пустой diff не является успешной проверкой.
- Прочитать полный согласованный source issue/spec/ticket, non-goals и явные
  уточнения. Если source удалён по completion protocol, восстановить точную
  согласованную версию из Git; не выдумывать её из итогового отчёта.
- Сохранить исходный scope/manifest, источник требований, решения по companion
  изменениям и одну таблицу requirement -> evidence. Для каждой проверки
  записать inputs, конфигурацию/toolchain, команду, exit и артефакты.

## Сохранение и передача приёмки

До первого запуска прочитай [контракт сохранения evidence](references/acceptance-evidence.md).
Если implement передал manifest, сначала прочитай его и проверь применимость
существующих результатов. Сохраняй отчёты каждой проверки до следующего запуска,
который может их перезаписать. В итоговую передачу включи manifest, отдельные
отчёты review-осей и оставшиеся действия завершения с ответственным этапом.

## Предварительная готовность гейтов

До дорогих запусков определи обязательные для текущей задачи гейты по правилам
проекта и согласованным требованиям. В существующем manifest отметь их статус,
доступную evidence и известные препятствия; отдельный реестр не создавай.
Недоступность runner не делает обязательный гейт неприменимым.

Заранее проверь то, что можно установить без запуска scan и передачи source:
scope/base, наличие runner и инструментов, конфигурацию Sonar и endpoint,
предусмотренный способ передачи credentials и уже действующую авторизацию,
не извлекая значения секретов. Не обходи ограничения доступа. Уже данное
разрешение не запрашивай повторно; неизвестное на этом этапе выясняй штатным
запуском, когда он разрешён.

Обнаруженный блокер сообщи сразу и зафиксируй в manifest. Продолжай независимые
разрешённые проверки, если они дают полезную evidence. Пока обязательный гейт
недоступен или не выполнен, общего PASS нет.

## Первый проход: собрать findings

1. Если изменился код, сначала выполнить дешёвые lint/compile/targeted checks
   по карте затронутых старых и новых контрактов. Не запускать широкую сборку
   поверх уже известного lint или test failure.
2. Получить текущий build/tests/detekt и OWASP через `scripts/pipeline-verify`
   (либо эквиваленты из guide). Уже успешный build для тех же inputs может быть
   принят по сохранённому результату; Gradle также переиспользует outputs.
3. После успешной механики получить scoped Sonar findings **до первого
   semantic review**, когда Sonar доступен. Его code findings не мешают двум
   review-осям собрать независимые замечания. Не исправлять код одновременно
   с ревью: все смотрят один snapshot. Sonar infrastructure failure фиксировать
   отдельно; review может продолжиться, но общий PASS невозможен.
4. Запустить `two-axis-review`: две независимые параллельные оси Standards и
   Spec. Первый проход полный. Передать machine findings как уже известные,
   чтобы не дублировать lint; не подсказывать желаемый semantic verdict.
5. Собрать разрешённые findings в одну remediation-волну. Механический сбой,
   мешающий выполнить последующие проверки, сначала устранить отдельно.

Sonar дорогой полный cold run не требуется до каждого targeted изменения:
ранний scan нужен на готовом к ревью snapshot; дальше повторять по изменившимся
inputs. Если пользователь явно исключил Sonar, отметить NOT RUN, не полный PASS.

## Контракты механических гейтов

`scripts/pipeline-verify`: build/tests/detekt и OWASP. Перед запуском проверить
явный `dependencyCheck.failBuildOnCVSS` в диапазоне 0-10; default 11 является
report-only. Отсутствующий порог требует согласования security policy. Сбой NVD,
registry, сети или cache является infrastructure failure, не behavioral RED.

Предпочесть `scripts/pipeline-sonar`; fallback:
`$HOME/.agents/skills/verify-changes/scripts/pipeline-sonar`. Fallback читает
секреты только из `$HOME/.config/verify-changes/sonar.env`. Для named base
передать `VERIFY_BASE_REF=<ref>`; без него используется dirty diff к HEAD.

Sonar пишет `build/pipeline/sonar/verdict.json`: блокируют scoped
`blocking_issues` и `blocking_hotspots`. Общий `quality_gate` информационный;
baseline вне scope не блокирует. `UNKNOWN`, неконсистентный API, недоступный
runner или пустой scope не являются PASS. Сохранить verdict и нужные правила
в evidence-пакете перед следующим scan, который может перезаписать рабочие reports.

Коды репозиторных pipeline scripts: 0 PASS, 1 findings/непройденный гейт,
2 configuration/infrastructure failure. Для 1 классифицировать фактическую
причину по логам; не выдавать произвольный network/tool failure за дефект кода.
Pitest в pipeline не входит.

## Долгие команды

Использовать repository `scripts/check-run`, если он доступен, и его справку.
Он сохраняет command, input snapshot, log, время и exit независимо от жизни
интерактивного terminal. Секреты передавать через предусмотренное окружение,
не через сохраняемые argv; отчёты не должны содержать raw env dumps.

Предпочитать completion notifications. Если harness требует polling, выполнять
одно ограниченное ожидание в полезной точке и согласовать его timeout с yield
внешнего exec. Не создавать дополнительные короткие wait-циклы и не перечитывать
неизменный stdout. Делать независимую работу во время ожидания, без параллельного
Gradle в том же checkout. Финальный exit обязателен; XML сам по себе его не заменяет.

## Исправления и повторное использование результатов

Следовать выбранному в проекте режиму `tdd`:

- bug/изменение известного ошибочного поведения: причинный regression RED, fix,
  тот же GREEN и affected contracts;
- новая согласованная функциональность: небольшие behavior-first slices либо
  strict TDD, если его требует пользователь/репозиторий;
- pure refactoring: существующие GREEN tests; docs/KDoc-only: diff/link/validator
  и другие реально затронутые проверки, без искусственного RED.

Закрывать связанные findings coherent slices; каждый получает узкую проверку.
Не запускать полный pipeline после каждой правки. По завершении волны составить
delta и определить, какие прежние результаты она инвалидирует:

- runtime/test/build/toolchain changes: affected tests/lint и необходимый build;
- shared helper/contract: расширить проверку до consumers и обеих затронутых осей;
- docs/UML-only: docs/links и contract review; неизменные runtime results остаются;
- dependencies/security configuration: OWASP заново; неизменный актуальный scan
  можно принять только при той же policy, dependency graph, analyzer и допустимой
  по проектной policy свежести vulnerability data;
- Sonar inputs/configuration: повторный scoped scan; не принимать старый verdict
  за анализ изменённого source.

Input hashes необходимы, но недостаточны: проверить целостность outputs,
toolchain/environment и freshness внешних данных. Неизвестная применимость
требует повторной проверки. `check-run` не принимает такие semantic решения.
Не ослаблять coverage/security thresholds, не обновлять approved fixtures под
ошибочный actual output и не убирать обязательные process/OCI/lifecycle checks.

Продолжать **тех же двух рецензентов** с delta, их предыдущими findings,
затронутыми контрактами и актуальной evidence. Неизменные части сохраняют verdict
первого полного review. При потере контекста/manifest или широком изменении
границ выполнить новый полный проход. Оси не объединять.

Повторная та же finding без прогресса на втором проходе: остановиться и сообщить
конкретную причину. Изменения после проверки требуют нового анализа влияния.

## Findings и завершение

Сохранить severity и независимость осей. Блокируют жёсткие нарушения стандартов,
невыполненные/частичные требования и non-goals. Fowler judgement calls,
пограничный gold-plating и спорный companion scope требуют решения пользователя;
ранее принятое решение не становится новым blocker.

Перед исправлением по LLM finding или признанием её блокирующей сверь указанное
правило/требование с исходным документом, а ссылку на код - с проверяемым diff.
Утверждение об ошибочном поведении подтверди адресной проверкой, когда одного
чтения недостаточно. Это проверка оснований находки, не третье полное ревью:
исходные отчёты Standards и Spec сохрани отдельно и не переранжируй.
В manifest отметь подтверждённую, опровергнутую или неразрешённую находку с
причиной; неверная ссылка сама по себе не опровергает риск. При недостаточной
evidence уточни находку у той же review-оси.
Опровергнутая находка не блокирует PASS. Неизвестный статус обязательного
требования не считай выполненным и не объявляй полный PASS.

Каждой finding назначить один primary prevention tag: `canonical-reuse`,
`evidence-integrity`, `contract-drift`, `lifecycle-determinism`, `scope` или
`static-analysis`. Tag не меняет severity и не объединяет оси.

Перед PASS подтвердить конечный scope и полную применимость всех результатов.
Отчёт: ссылка на сохранённый manifest, статус каждого gate, artifact и проверенные
inputs; что выполнено заново,
что переиспользовано и почему; remediation waves, full/delta review passes,
findings по prevention tags и остающиеся ограничения. Не называть rerun то,
что было принято по прежней evidence. Skill не выполняет доставку.

При явном «закрой issue по пайплайну» после прохождения гейтов проверь, что
согласованный source восстанавливается так, как требует проект. Выполни
протокол завершения issue, включая перенос требований и изменение статуса или
каталога. Проверь ссылки и валидатор итогового состояния, затем оцени, какие
результаты closure-правки инвалидировали; получи недостающую evidence до
объявления финального PASS и закрытия. Если source или обязательный гейт
недоступен, оставь issue открытой и назови блокер. Без явного запроса на
закрытие сообщи результат проверки и оставшиеся действия, не меняя статус.
Новые правила автоматически не добавлять.
