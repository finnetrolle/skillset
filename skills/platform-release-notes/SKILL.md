---
name: platform-release-notes
description: Составлять краткие release notes платформы на русском по Git-истории нескольких репозиториев, объединяя указанные версии без повторов. Использовать для просьб «список изменений выпуска платформы», «release notes по всем проектам» или «включи изменения предыдущей версии». Не предназначен для публикации релиза или изменения кода.
---

Собери проверяемый состав выпуска и преврати его в короткий пользовательский список изменений. Номер выпуска платформы может отличаться от версий её компонентов. По умолчанию пиши по-русски, простыми словами, без длинного тире.

**Границы выпуска**

- Из запроса и контекста определи платформу, целевую версию, включаемые предыдущие версии и рабочую папку. Если существенные данные отсутствуют и не выводятся из контекста, задай короткий вопрос, продолжая независимую инвентаризацию.
- Если речь о всей платформе, проверь все входящие в неё репозитории. Родительская папка может не быть Git-репозиторием; у соседних каталогов могут быть независимые истории и версии. Учитывай `.git` как каталог или файл. Не создавай Git в корне и не считай случайные вложенные зависимости компонентами платформы.
- Прочитай применимые инструкции. Найди существующий состав релиза: манифесты, списки задач, матрицы по репозиториям, release notes и release-ветки. Используй их для определения состава и поиска пропусков, а не как самостоятельное доказательство доставки кода.
- Не закрепляй в скилле номера версий, список репозиториев или абсолютные пути из прошлой беседы. Для новой версии обнаруживай их заново.

**Подтверждение изменений**

- Проверяй Git без переключения веток. Просматривай состояние рабочего дерева, теги, release-ветки и историю слияний; текущий checkout или `dev` могут не соответствовать выпуску. Незакоммиченные изменения не включай в опубликованный состав.
- Предпочитай зафиксированный релизный манифест и конечные теги. Аннотированный тег разрешай до коммита через `^{commit}`. Если тега ещё нет, используй согласованную release-ветку и обозначь результат как предварительный.
- Для актуального состава при необходимости обнови ссылки штатным `git fetch` без принудительной перезаписи тегов и удаления ссылок. Если сеть недоступна, работай по доступному снимку, указав его границы. Не выдавай локальную историю за свежую проверку сервера.
- Определи базу сравнения отдельно для каждого компонента по предыдущему релизу. Не применяй автоматически один номер, дату или `HEAD^1` ко всем репозиториям. Если базы нет, опирайся на подтверждённый состав задач и явно сохрани это ограничение в источниках.
- Сначала прочитай краткую историю подходящего диапазона. По ключам задач найди реализацию, при необходимости прочитай тело merge-коммита и diff. Не выводи целиком большие changelog и логи: извлекай только нужные разделы.
- Наличие задачи в любой ветке или статус Closed в старой выгрузке не доказывает включение в релиз. Подтверждай достижимость коммита из конечной ссылки (`merge-base --is-ancestor`), эквивалентный cherry-pick или реализацию в конечном дереве. Учитывай последующие откаты и замены.
- Разные SHA после слияния допустимы: при проверке одинакового содержимого сравнивай деревья через `git diff`, а не только хеши коммитов. Различай найденный diff и ошибку команды.
- Если компонент имеет собственную версию, укажи её корректно. Например, версия CLI может отличаться от номера всей платформы. Совпадение деревьев release-ветки и тега подтверждает содержимое, но само по себе не подтверждает развёртывание.
- Для каждого утверждения сохрани связь с репозиторием, конечной ссылкой, коммитом и задачей, если она известна. Не раскрывай секреты из настроек, remote URL или журналов.

**Объединение нескольких версий**

- Если пользователь просит включить предыдущую версию в новую, собери объединение подтверждённых изменений всех указанных выпусков. Одного диапазона «предыдущая версия..новая версия» недостаточно: он исключает саму предыдущую версию.
- Сверь весь исходный список задач с конечным результатом. Каждая задача должна быть покрыта пунктом, объединена с тем же исправлением или иметь объяснение отсутствия подтверждения в файле источников.
- Дополнительно проверь изменения, вошедшие в релиз после подготовки старого списка. Не ограничивай выпуск перечнем из сохранённой матрицы.
- Объединяй связанные изменения разных сервисов по пользовательскому результату. Сквозная трассировка семи сервисов обычно является одним пунктом, а не семью одинаковыми пунктами.
- Не включай отменённые изменения как действующие. Репозитории без изменений или с неподтверждённым участием отметь в источниках; не придумывай для них пункты release notes.

**Краткие release notes**

- Начни с названия платформы и версии. При объединении добавь одну строку: «Выпуск включает изменения версии ...».
- Основной формат: короткий маркированный список «**Компонент или возможность.** Что добавлено, улучшено или исправлено». Для обычного выпуска ориентируйся на 6-12 пунктов, объединяя близкие изменения без потери смысловых групп. Не растягивай маленький выпуск до этого объёма.
- Пиши о наблюдаемом результате: «Исправлена отправка готовых файлов», «Добавлена оценка ответов». Не заменяй конкретику пустыми фразами вроде «Улучшено качество платформы».
- Переводи технические детали в понятный результат, сохраняя названия продуктов и необходимые форматы файлов. SHA, номера задач, PR, ветки, пакеты и внутренние контракты оставляй в источниках, если пользователь не запросил технический вариант.
- Не обещай больше доказанного: добавление правил сохранения оформления не означает гарантированное сохранение любого документа; исправление одной причины сбоя не означает устранение всех сбоев.
- Указывай ограничения рядом с пунктом, только если без них описание вводит читателя в заблуждение. Не добавляй общий технический аудит или неподтверждённые утверждения об успешном тестировании и развёртывании.

**Результат и проверка**

- По умолчанию сохрани готовый Markdown в `outputs/release-<version>/RELEASE_NOTES_<version>.md` текущей рабочей области и дай полный краткий текст в ответе вместе со ссылкой на файл. Если пользователь задал путь или просит только текст, соблюдай его выбор.
- Для состава из нескольких репозиториев сохрани рядом небольшой `release-evidence.md`: дата снимка, база и конечная ссылка каждого компонента, подтверждения пунктов, покрытие включаемых версий и существенные пробелы. Не загружай публичные release notes этим реестром. Полные выгрузки Git нужны только при отдельном запросе.
- Перед сдачей проверь покрытие исходного состава, отсутствие повторов, корректность версий и соответствие каждого пункта конечному коду. Объединённый текст не должен случайно терять изменения включённой предыдущей версии.
- Для этой задачи достаточно чтения истории и записи артефактов. Не запускай платформу, сборки, миграции или стендовые тесты только ради release notes. Не меняй исходники, теги, релизные статусы или вручную `CHANGELOG.md` и generated files. Публикация, рассылка и изменения во внешних системах требуют отдельного запроса.

Пример запроса: «Составь release notes платформы 0.7.1 по всем проектам; изменения 0.7.0 тоже включи. Кратко, на русском».
